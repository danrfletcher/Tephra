# Architecture

Tephra is a federated link and graph engine for plain-text knowledge: a background daemon (`tephrad`) that indexes any number of folders ("sources") into one link graph, and a command-line client (`tephractl`) that talks to it. Obsidian vaults, code repositories and plain folders are treated as equal siblings in one namespace.

This page describes `main`. What is not built yet is listed in [Not built yet](#not-built-yet).

```
 tephractl  ──┐                          ┌─ source "notes"      (a folder of notes)
 (CLI)        │  JSON-RPC 2.0            ├─ source "atlas-repo" (a code repository)
 future       ├─ HTTP + WebSocket ──►  tephrad ──► watcher ─► parser ─► SQLite cache ─► in-memory graph
 clients      │  127.0.0.1:4812,        (daemon)        ▲                                   │
              │  bearer token                           └──────── graph:changed (push) ◄────┘
              ┘
```

## Crates

| Crate | Job |
|---|---|
| `tephrad` | The daemon: config and auth token, source registry, filesystem watcher, JSON-RPC server. Headless by design: no UI of any kind. |
| `tephra-parser` | Pure parsing, no I/O and no resolving. Markdown (`pulldown-cmark`): frontmatter, headings, `[[wikilinks]]` (including `[[@source:path]]` and `[[path#^id]]`), `[markdown](links)`, `#tags` and `^block` ids, with every occurrence of an ID kept. Code (tree-sitter, 13 languages): symbols, comment blocks and `// ^id`, `# ^id` and `-- ^id` block IDs. Text of `.docx`, `.pptx` and PDF documents by paragraph, slide or page. |
| `tephra-cache` | The SQLite database (WAL mode): sources, units (each with a kind, size and `too_large` flag), links, tags, blocks, headings, symbols, a trigram full-text table and per-source scan state. Schema version 2. Versioned: on a schema change it drops and rebuilds rather than migrating, and tries to keep the rows of offline sources. |
| `tephra-graph` | The in-memory link graph built from the cache: forward links, backlinks, tags, and the link resolver. |
| `tephra-remote` | Read-side adapters for GitHub and Google Drive, and what they stand on: the credential-store trait (macOS Keychain; a file store only behind the `test-credential-store` feature) and the API-URL rule, both re-exported by `tephrad`. The adapters read one named repo or one Drive folder, never write, never follow a redirect and never sleep: a rate limit (E1) is answered as `RateLimited { retry_at }` and a rejected token (E2) as `AuthRejected`, latched until the stored token changes. A non-default base URL is accepted only for a loopback host. In-process fake GitHub and Drive servers (feature `test-support`, loopback only) back the tests. Depends on neither `tephrad` nor `tephra-cache`. |
| `tephractl` | The CLI client: `source add/remove/list`, `status`, `ls`, `search`, `link resolve`, `link refactor`, `block-id`, `backlinks`, `daemon install/uninstall/status` and `auth github/google/status/logout`. Holds no state (the `auth` commands keep the GitHub and Google credentials in the macOS Keychain through `tephra-remote`, need no daemon and open a socket only for `auth google`'s loopback redirect on `127.0.0.1`); every change to your files is made by the daemon (see [What Tephra writes](#what-tephra-writes)). |

## How a source plugs in

1. `tephractl source add notes /path/to/notes` calls `source.register`. The name becomes a namespace: every note in it is addressed as `@notes:path/to/note`.
2. `tephrad` walks the folder. Ignored names (`.git`, `node_modules`, `target`, `.venv`, `__pycache__`, `.DS_Store`, `Library` and `.Trash` directly under `$HOME`, plus anything listed in a `.tephraignore` at the source root) are pruned before the walk descends into them, and the walk streams rather than collecting every path first. Every other file becomes a unit with one of five kinds: `prose` (Markdown and other text notes), `code` (13 languages, read with tree-sitter), `document` (`.docx`, `.pptx` and PDF, read for their text), `text-other` or `binary`; a folder is listed as a `folder`. Files over 20 MiB (the 20 MB cap) are indexed by name only.
3. Each `prose` and `code` file is parsed to a unit and written to the cache with its links, tags, headings, symbols and blocks; a document is written with its text by page, slide or paragraph; a `text-other` file is searchable by blank-line-separated block; a binary or too-large file is written as a unit with its name, kind, size and mtime only. The cache is SQLite schema version 2: a cache from an older version is rebuilt, and every source is rescanned as if it were new. A scan records when it starts and finishes, and the daemon rescans any source whose scan never finished (for example after a `kill -9`) on its next start. A `notify` watcher keeps it current: filesystem events are debounced (250 ms) and coalesced, the file is re-parsed, and the graph is updated. Connected WebSocket clients get a `graph:changed` notification: `{source, paths}`, the source and the files that changed, after the in-memory graph is refreshed. When Tephra's own link fix has something to report, the same notification also carries `fixes`, a list with one entry per rename fixed: `{kind, source, old, new, files_changed, status, deferred}` (and `new_source`, only when a move crosses sources). `kind` is `rename` (a folder rename is one entry with the folder's old and new path); `status` is `applied`, `partial` or `needs_manual_fix`, as in the fix log; `files_changed` counts only the files actually rewritten and `deferred` the linking files left for a retry or a person (0 when every file was written). Then `paths` are the files the fix rewrote. A fix batch makes ONE notification, however many renames or files it holds; the log entry is written and the graph refreshed before it is sent, so a client that re-queries on receipt sees the new links and `fix.list` already holds the entry. A retry that finishes leftover work sends its own entry (`applied`, `deferred` 0). A push with no fixes (an ordinary edit) has no `fixes` key and is unchanged, so a client that ignores `fixes` is unaffected. The push is data only and is never waited on: with no client, an HTTP-only client or a lagging one it is dropped and the fix and its log entry stand. The fix's own writes are recorded (path, size, mtime) as Tephra's own, so the watcher drops their events and they start no second push and no further fix; an edit made to a file after the fix wrote it is not dropped. A change to the list of sources sends ONE `graph:changed` of its own, with the same `source` and `paths` (`paths` empty: the whole source) and a `sources_changed` list, `[{kind, name}]`: `source.register` sends `added`, `source.unregister` of a registered source sends `removed`, and a rename sends `renamed` with the new name in `name` and the old one in `old_name`; `source.promote` sends `promoted` and `source.unpromote` sends `unpromoted` (and so does `source.unregister` of a promoted source). It is sent by the registry after the change is made, so every caller of `register` and `unregister` pushes (`tephractl source add` and `remove` included, with no client involved), and it goes out after the in-memory graph is refreshed, so a client that re-queries `source.list` or `unit.resolve_link` on receipt already sees the change. A register that fails or is rolled back, an `unregister` of a name that is not registered, a restart, a rescan, a file change and a fix send no `sources_changed`. The push is dropped when no client is listening. A client that ignores `sources_changed` re-queries as before.
4. If a source's folder goes missing (an unmounted drive), the source is marked offline. Its cached index is kept, and links into it resolve with an `(offline)` marker until it returns.

Sources are independent: a missing or broken source does not corrupt another.

## How links resolve

- `[[Note]]` (no prefix) resolves within the note's own source, by file name or path, shortest path first. If two files tie, the resolver returns an error listing every candidate rather than guessing.
- `[[@atlas-repo:README]]` resolves in the named source. Reaching across sources needs the explicit `@source:` prefix; there is no search across all sources for an unprefixed link.
- A target that matches nothing is reported as unresolved, which is a different result from ambiguous.
- `[[@source:path#^id]]` links to a block (write block links as `[[path#^id]]`, or with the `@source:` prefix to reach another source). The named file is looked at first (`block {id, line, moved: false}`; for a code file `line` is the definition's first line, the one that carries the ID comment). If the ID is not there and is a Tephra ID (exactly 6 characters of `a-z0-9`), the one other file of the same source that has it is the answer, with `moved: true`; two or more files, or one file with the ID twice, is an ambiguity error that lists every file and line, never a guess. A typed ID such as `^summary` missing from its file is unresolved, whatever other files hold, and the search for a moved ID never leaves the source. `#Heading` and `#symbol_name` anchors resolve to the file and carry `block: null`. `[[path^id]]` (no `#`) is never a block link.
- **Duplicate block IDs.** Within one file, a duplicate is renamed (see [What Tephra writes](#what-tephra-writes)); across files it is allowed, and resolving it gives the ambiguity error above. A file that already held a duplicate when it was first scanned is left as it is, and resolving that ID lists every line.
- `graph.get_backlinks` takes a unit id (`@s:path`, every link to the file, anchored or not) or a block id (`@s:path#^id`, only links to that block, including links written to the block's old file that find it here as `moved`). Each row has the `line` of the link (1-based; `null` for a link in a document, which has pages, not lines), and there is one row per `(from, line)`. The cache keeps the line in `links.line`; a cache without it is rebuilt, and an offline source's links come back with `line` null until its next scan. `tephractl backlinks <id>` prints it.

## The RPC surface

JSON-RPC 2.0 over HTTP (`POST /rpc`) and WebSocket (`GET /rpc`) on `127.0.0.1:4812`. Every call needs the local bearer token (a file in the daemon's data directory, mode 0600); it is re-read and checked on every HTTP request and every WebSocket message. The method set is a closed list of 19 (`METHOD_NAMES` in `crates/tephrad/src/rpc/dispatch.rs`, with a test that the dispatch table is exactly that set):

- `source.register`, `source.unregister`, `source.list`, `source.rescan`
- `source.add_github` (`{name, repo, branch?}`): register ONE GitHub repository on ONE branch (default: the repo's default branch). `repo` must be exactly `owner/repo`: an owner alone, `owner/*`, `*/*`, a URL or `owner/repo/extra` is refused with `data.reason` `pick_one_repo` and no request is made to GitHub (no list-all-repos call exists). The name follows the local rules (same checks, same case-insensitive collisions, across local and remote sources). Before anything is stored the daemon checks, with plain reasons in `data.reason` (`auth_required` for no token and for a rejected one, `permission_denied`, `not_found` (no access looks the same as not found, and the message says so), `unknown_branch`, `repo_moved`, `rate_limited`, `invalid_name`, `name_taken`; any other failure is `could not reach GitHub`): the token, the repo, the branch, then lists the WHOLE tree at the branch's head commit (a truncated recursive listing is finished level by level, so no file is lost or doubled; an empty repo, which GitHub answers with 409, registers with 0 files). A refusal changes nothing. The listing is stored as units in state `remote` (kind from the file name alone; size from the tree; 0 bytes cached; no path on disk; symlinks and submodules listed by name, never followed or fetched) and the call returns `{name, kind: "github", repo, branch, commit, files, status, index_done, index_total}` within seconds. A background job then reads each text file once through the API by the blob sha taken at listing (so a branch that moves mid-index never mixes commits), parses it with the same parsers as a local file into links, headings, blocks and symbols, and drops the bytes: no file is created under the data dir. A file over the index cap, a known-binary extension, an LFS pointer and a submodule are listed by name only and never read. `source.list` shows the row with `kind`, `repo`, `branch`, `cache`, `cache_bytes`, `git_bytes`, `status` (`indexing` with `index_done`/`index_total`, then `active`) and `last_scanned_at`; `unit.list` shows `state`, `cache_bytes` and `reason` per entry and never calls GitHub. A rate-limit answer during indexing backs off and the index goes on; a token that goes bad sets `auth_required`. At the next start the daemon answers `source.list` and `unit.list` from the cache with no GitHub call, and a first index that was interrupted is finished then (polling and offline handling come later). A remote source is not renamed, removed, rescanned or watched in this version, and no remote file is ever written, moved or renamed. A vault link `[[@<name>:README.md]]` resolves like any other, and backlinks work both ways. `tephractl source add github <name> <owner/repo> [--branch <b>]` calls it.
- `unit.fetch` (`{unit}`; `unit` is `@source:path`): puts one file of a remote source in Tephra's content cache, `<data_dir>/remote/<source>/` (GitHub files under `clone/`), at the same relative path, and answers `{unit, path, state, size}` once it is there: `path` is absolute, `state` is `cached` (or the file's own state when it holds edits that are not pushed yet: such a file is returned as it is and never overwritten). It is the only call that downloads a file: nothing is fetched in the background. The body is streamed to a temporary file in the same directory, checked against the listing (size and git blob id), fsynced, renamed into place and the directory fsynced, so a reader never sees half a file; a failure leaves no file and no temporary file, the item `remote`, and the reason in `unit.list` (`reason`, starting `fetch failed:`). Fetches of one file at the same time share one download and one result. Every remote name is mapped to a safe path: `/`-separated parts only, `.`/`..`/empty/control characters/`\\` escaped as `%XX`, `%` itself as `%25`, a `.git` part as `%2Egit`, a name over 255 bytes cut with a hash tail, names that differ only by case kept apart; the mapping is deterministic and never leaves the cache root, and a symlink inside it is never followed. A refusal is a `SOURCE_ERROR` (-32011) with `data.reason`: `unknown_unit`, `not_remote` (a file of a local source), `not_fetchable` (a Google Doc, Sheet, Slides, Forms or Drawing, a shortcut, a symlink, a submodule or a Git LFS pointer; `data.url` is where to open a Google file, `data.kind` says what it is), or why a download failed (`auth_required`, `permission_denied`, `remote_missing`, `server_error`, `rate_limited`, `offline`, `connection_dropped`, `corrupt_body`, `disk_full`, `disk_error`, `unsafe_path`, `in_the_way`). No credential is in any of them.
- `cache.status` (no params): what the content cache of remote sources takes, read-only: `{cache_bytes, limit, limit_bytes, over_limit, pinned_bytes, git_bytes, idle_seconds, warning?, sources: [{name, cache, cache_bytes, git_bytes}]}`. `cache_bytes` is the total of the files in state `cached` (the bytes the limit is measured against). `over_limit` is true while `cache_bytes` is above `limit_bytes` and says nothing else. `git_bytes` is what the `.git` folders of the clones take: it is NOT counted toward the limit, is shown on its own and is never evicted (a GitHub source holds plain downloaded files under `clone/`, so it reads 0, until Dan makes a real git clone there: then it is that clone's `.git`). `warning` appears when pinned files alone take more than the limit: nothing pinned is ever dropped, so the cache stays over the limit and the unpinned files go first.
- `cache.set_limit` (`{limit}`): changes the limit at once, saves it to `cache_limit` in `config.toml` (the whole file is checked and written through a temporary file and a rename, so a failed save leaves the old file and the old limit), and runs an eviction pass without waiting. `limit` is a number and a unit: `MB` and `GB` (1000-based), `MiB` and `GiB` (1024-based), case-sensitive, one optional space; `0` is accepted (it drops every file that is allowed to go; the same rule loads a `cache_limit = "0"` from the config file). `abc`, `-5MB`, `1.5.2GB`, an empty value, a number without a unit and a value above the largest `u64` are refused with a `SOURCE_ERROR` (-32011) whose `data.reason` is `bad_limit` and whose message says why and names the limit that stays; nothing changes. It answers what `cache.status` does plus `{previous, dropped, freed_bytes}` for the pass it ran. The default limit is 10 GB.
- `source.set_cache` (`{name, cache}`, `cache` a boolean): the per-source cache flag, default on, kept across restarts in the cache index. With it on, a fetched file stays until the limit needs the room. With it off, a fetched file is dropped about 10 minutes after it was last used, whether or not the cache is over the limit; turning it on again ends those drops. It answers `{name, cache, was, dropped}` and runs a pass at once. A name that is not a source is `unknown_source` and a source on a local folder is `not_remote`, both with a plain message and nothing changed. `source.list` and `unit.list` show the flag as `cache`, with `cache_bytes` and `git_bytes`. `tephractl cache on|off <source>` calls it.
- Eviction (G12, G20). A pass runs every 30 seconds and right after `cache.set_limit` and `source.set_cache`. It drops cached files, least recently used first (`last_used`, set by `unit.fetch`), until the total is at or under the limit; a source with its flag off has every idle file dropped whatever the total. A file is NEVER dropped when: it is pinned, or sits under a pinned folder (a pin wins over the limit and over the flag); it holds edits that are not pushed (`pending_upload`, `not_pushed`, or a queued edit); it is being downloaded; or it was used in the last 10 minutes. So the cap is soft: a fetch never fails or waits because of it, the cache can sit over the limit for up to 10 minutes, and a pass that finds nothing to drop writes nothing. Dropping a file means: check that the copy is still what Tephra wrote (a GitHub file by git blob id; a Drive file by a hash of its bytes noted in the cache index when it was downloaded, because a Drive listing has no checksum and a size alone misses an edit of the same length; a changed file, or a Drive file with no hash noted, is treated as a local edit and kept), claim the row with one conditional update (`cached` to `remote`; a fetch that touched `last_used` after the pick wins and the file stays), check again, delete the file through the same path rules as `unit.fetch` (never outside `<data_dir>/remote/<source>/`, a symlink is never followed), then remove the folders it left empty, up to but never including the cache root or a `.git`. The item goes back to `remote`: it stays in `unit.list`, keeps its size and its backlinks, and `unit.fetch` brings it back. A delete that fails (permission, I/O) puts the row back to `cached` and logs the reason; a crash between the delete and the row update is repaired at the next start (a `cached` row whose file is gone becomes `remote`; a `remote` row whose file is still there and is still what Tephra wrote becomes `cached` again, so it counts toward the limit and can be dropped again; a file that differs is left exactly as it is), with no byte counted twice or below zero. Eviction makes no request at all to the remote: it works with the source `offline` or `auth_required`, and it never deletes, moves or renames anything on GitHub or Drive. It writes no git data, and a clone that has a `.git` is never evicted from (its files are Dan's working tree, not a cache). The test-only config key `cache_idle_seconds` (1 to 86400) shortens the 10 minutes; it is not meant for use.
- A GitHub source's git clone (G13, G15, E12, E23). Tephra never creates a clone: when Dan has made one himself at `<data_dir>/remote/<source>/clone/` (a `.git` directly in it, not a link), the daemon looks after it; a `clone/` without a `.git` is the plain cache above and none of this applies. The numbers: `source.list` and `unit.list` carry `not_pushed` (the files that differ from the remote tip) and `behind` (commits of the tracked branch the clone lacks), both left out of `unit.list` and 0 in `source.list` for a source with no clone. `not_pushed` counts every file Dan changed since the merge base of his HEAD and the tip: edits (staged or not), new files, deleted files, and files that exist only in unpushed commits; a file edited and committed counts once, and an untracked file that is byte for byte the tip's own does not count (decided from one `git diff --raw` of HEAD and the tip: no git call per file, so 10,000 new files count in well under 5 s). Each counted file has item state `not_pushed` (precedence `needs_attention` > `not_pushed` > `downloading` > `pinned` > `cached` > `remote`; a `pending_upload`, `downloading` or other-reason `needs_attention` file keeps its own state), and goes back to `pinned`, `cached` or `remote` when its content is the tip's again. `tephractl source list` prints `<name>: N changes not pushed` (`1 change not pushed` for one, no line for 0) and `<name>: behind by N` under the source. The count is redone after every sync (the 60 s poll, whether or not the API poll found anything) and about 250 ms to 1 s after a save in the clone (the watcher's debounce; events under `.git` are dropped), and it survives a restart in the `remote_clone_state` table. The pull rules, on every sync: `git fetch` of the tracked branch (it writes only inside `.git`); then, ONLY when the clone is on the tracked branch, clean (no tracked edit, no untracked file) and strictly behind (behind, not ahead), `git merge --ff-only --no-overwrite-ignore` (git then also refuses to replace one of Dan's ignored files, such as a `.env` upstream starts tracking; the pass leaves it, and the clone stays behind), after which cached files hold the new content, the listing updates and `graph:changed` goes out. In every other state (local commits, edits, untracked files, ahead and behind, another branch) nothing in the clone moves: the working tree, index, HEAD, branch and reflog are exactly as they were, and `source list` shows `behind by N`. When both sides have commits the other lacks, the source stays `active` and carries the note `the clone and GitHub have diverged; ... run `git pull --rebase` in the clone yourself`: that note is the only guidance, Tephra merges and rebases nothing, and `git rev-list --merges` stays empty. A file changed on both sides since the merge base is `needs_attention` with the reason `changed locally and on GitHub; run `git pull --rebase` in the clone yourself ...`; a file changed on one side keeps its normal state. A force-push (the tip recorded at the last good pass is not an ancestor of the new tip, whether the branch was replaced or moved back so the new tip is an ancestor of the old one) is never pulled, whatever the clone's state: the source goes `needs_attention` with the reason `history rewritten on GitHub; ... run `git pull --rebase` yourself ...`, nothing in the clone is touched, and the old tip stays recorded so the flag stays until Dan's own git moves the clone off the old history (HEAD no longer holds the old tip and is the new tip or has it below his commits). A clone that is not on the tracked branch, a failed fetch (`offline` or `auth_required` with a reason starting `git fetch failed:`; the last counts are kept) and a clone in the middle of a rebase, merge, cherry-pick or revert (or holding `index.lock`: that pass is skipped) are told the same way or left alone. These statuses are written only over `active` or over a status this pass wrote, so the poller's own statuses and this pass never overwrite each other, and a poll that sees a file deleted on GitHub never deletes a file in a clone. Tephra never commits, pushes, rebases, resets, stashes, checks out or force-fetches: the only git commands the daemon runs are `fetch`, `rev-parse`, `rev-list`, `merge-base`, `diff`, `status`, `ls-files` and `merge --ff-only --no-overwrite-ignore <ref>`, checked against an allowlist before a process starts (`crates/tephrad/src/remote/clone_state.rs`), with no token on any command line (git uses the clone's own `origin` and credential helper). A `git` program other than the one on the path is a test hook only.
- `source.promote` (`{name, root}`): a folder strictly inside a registered source becomes the source `name`. `root` is made canonical like `source.register`'s (a symlink out of the parent is refused as `not_inside_a_source`). Ownership of a file is the deepest registered root containing it, so the folder's files leave the parent and the parent never scans, watches or lists the folder again (the `promoted_roots` table, which a cache rebuild never drops, says which folders a source gave up). It works at any depth and for a folder inside an Obsidian vault; a folder that already holds a promoted source is fine, and that source stays its own. The order is fixed: one transaction writes the registry row, the exclusion, the fix-log entry (kind `promote`: `old` is the folder's path in the parent, `new` is `@name:`) and the pending list of every link that has to change; then the cached units are re-owned in place (no file is ever in two sources); then each file is rewritten by the same write loop as any fix, with no approval step (a link that crosses the new border gains or changes its `@source:` prefix, and one inside the folder spelled from the parent's root becomes relative to the new root, shortest unique; anchors and aliases stay; only wikilinks change); then the new source is scanned and watched and ONE `graph:changed` goes out, with `sources_changed: [{kind: "promoted", name}]` and the entry in `fixes`. A kill after the transaction is finished at the next start (the rows are re-owned, then the pending list is retried). A refusal changes nothing and sends nothing; it is a `SOURCE_ERROR` whose `data.reason` is `is_a_source_root`, `not_inside_a_source`, `not_a_folder`, `not_readable`, `source_offline`, `invalid_name` or `name_taken` (compared without regard to case). `source.register` still refuses a root nested in, or above, a registered one: promote is the only way to nest. The reply is `{name, root, parent, folder, units_moved, files_changed, deferred, status}`. `tephractl source promote <name> <path>` calls it.
- `source.unpromote` (`{name}`): the reverse of `source.promote`. The promoted source `name` folds back into the source it was promoted out of, and the link rewrite goes the other way. The order is the promote's, with one difference: ONE transaction writes the fix-log entry (kind `unpromote`: `old` is `@name:`, `new` is the folder's path in the parent) and the pending list of every link that has to change, moves the cached files back to the parent under the folder, and removes the source's registry row, its `promoted_roots` row and the parent's exclusion of the folder (a file row cannot outlive its source, so the move is inside the transaction, not after it); then the promoted source's watcher stops and the parent's reads the folder again; then each file is rewritten by the same write loop as any fix, with no approval step (a link that crossed the border returns to `@parent:full/path` or to a shortest-unique name within one source; a link inside the folder loses the `@parent:` prefix, and one spelled from the folder's root becomes relative to the parent's root; anchors and aliases stay; only wikilinks change); then ONE `graph:changed` goes out, with `sources_changed: [{kind: "unpromoted", name}]` and the entry in `fixes`. A kill after the transaction is finished at the next start from the pending list. A source that was itself promoted out of `name` stays promoted and becomes a child of `name`'s parent. A refusal changes nothing and sends nothing; it is a `SOURCE_ERROR` whose `data.reason` is `unknown_source`, `not_promoted` (a normally registered source, or a promoted one whose parent was unregistered: it is top-level) or `source_offline` (the parent is offline). `source.unregister` of a promoted source does exactly this (same rewrites, same log entry, same push); of any other source it only deletes its rows, and an unregistered parent leaves the sources promoted out of it as independent top-level sources, with no rewrites. The reply is `{name, parent, folder, units_moved, files_changed, deferred, status}`. It is not an undo: the `promote` entry stays in the fix log, `unpromote` is a second entry above it, and there is no method that undoes or reverts a fix. `tephractl source unpromote <name>` calls it.
- `source.rename` (`{name, new_name}`): the source `name` is called `new_name` from now on, and every `@name:` link in every source is rewritten to `@new_name:`. It works for a normal source and for a promoted one. The order is the promote's: validate (a refusal changes nothing and sends nothing); pause the watchers; then ONE transaction renames the registry row and everything the cache holds by name (the `promoted_roots` rows and the pending list), writes the fix-log entry (kind `source_rename`: `old` is `@name:`, `new` is `@new_name:`) and stores the pending list of every file with a link to rewrite, so a kill after it is finished at the next start; the units and scan state belong to the source by id and do not move, so every `unit.list` and `source.list` id reads `@new_name:` at once and `@name:` no longer resolves; the source's watcher moves to the new name; then each file is rewritten by the same write loop as any fix, with no approval step; then ONE `graph:changed` goes out, with `sources_changed: [{kind: "renamed", name: new_name, old_name: name}]` and the entry in `fixes`. Only the prefix of a link changes: wikilinks, embeds (`![[@name:...]]`), frontmatter-property links and block links (`[[@name:path#^id]]`, anchor kept) are all rewritten, an alias is kept, a link in a code file changes in its comment text only, and a plain Markdown link or any prose around a link is never touched. A document (PDF, Word, PowerPoint) is never written: its links are logged `needs_manual_fix`. A file that is read-only, changed under the write loop, or in an unwritable folder is left (or retried, with bounded back-off) and the reply is `partial` with `deferred` set; the other files are rewritten. The rename's own writes are recorded as Tephra's own (path, size, mtime), so they start no watcher fix and no second log entry. `source.rename` to the source's own name is a success that does nothing: no rewrite, no log entry, no push. Rename, promote, unpromote and every other fix are serialised by one gate, never interleaved. The reply is `{name, new_name, files_changed, deferred, status}`. `tephractl source rename <old> <new>` calls it.
- Refusals (G14). Every refusal of `source.register`, `source.promote`, `source.unpromote` and `source.rename` is a `SOURCE_ERROR` (-32011) with a plain-English sentence in `error.message` and a stable string in `error.data.reason`, the same over HTTP and WebSocket. A client matches `data.reason`: `invalid_name`, `name_taken`, `not_inside_a_source`, `is_a_source_root`, `not_a_folder`, `source_offline`, `nested_source`, `unknown_source` or `not_promoted` (`source.promote` also answers `not_readable` for a folder it cannot read). `source.rename` can answer `invalid_name`, `name_taken`, `unknown_source` and `source_offline`; `source.promote` the path reasons and the name reasons; `source.unpromote` `unknown_source`, `not_promoted` and `source_offline`; only `source.register` answers `nested_source` (a root inside, or above, a registered one) or `is_a_source_root` (the same root). A new name is not empty, at most 64 characters, has no whitespace or control character, none of `/ \ @ : # ^ | [ ] *`, and is not `.` or `..`; it is compared without regard to case with every existing name, so `Notes` is taken when `notes` exists. The name rules apply to a new name only: a source registered under a name that breaks them is never re-checked, and can be renamed away. A refusal changes nothing: the registry, the cache, the files, the fix log and the pushes are as they were.
- `unit.resolve_link`, `graph.get_backlinks`, `graph.get_forward_links`, `graph.get_edges`
- `link.preview_refactor` and `link.apply_refactor` (`{source, old_path, new_path}`): the links a file move would break, and the rewrite that fixes them. See [What Tephra writes](#what-tephra-writes).
- `block.ensure_id` (`{unit, line}` or `{unit, symbol}`): gives a block an ID, or returns the one it has, as `{id, link, created}`. See [What Tephra writes](#what-tephra-writes).
- `fix.list` (`{since?, limit?}`): the fix log, newest first, as `[{id, time, kind, sources, old, new, files_changed, status}]`. `time` is epoch seconds; `kind` is `rename`, `move`, `promote`, `unpromote`, `source_rename` or `uncertain`; `new` is `null` for an `uncertain` entry, which also has a `message` saying why (for example `vanished, no certain pair: links broken`); no other kind has a `message`; `status` is `applied`, `partial`, `needs_manual_fix` or `uncertain`. `since` (epoch seconds, 0 or more) keeps the entries at or after it. `limit` is 1 or more, default 50, and anything over 1000 is cut to 1000; a `limit` of 0, a negative or fractional number, or a `since` that is not a non-negative integer is `invalid_params`. It only reads. `tephractl fixes` prints it. See [The fix log and pending fixes](#the-fix-log-and-pending-fixes).
- `link.rename_event` (`{old_path, new_path}`, two absolute paths): a client says a file or folder was renamed, and Tephra fixes the links to it now. It is exact: the two paths are the rename, and nothing is guessed from names or content. Each path is made canonical like `source.register`'s and placed in the source with the longest root (a symlinked or `..` route is the same source). The reply is exactly one of `{status: \"applied\", files_changed}`, `{status: \"partial\", files_changed, deferred: [{file, reason}]}`, `{status: \"already_applied\"}` or `{status: \"nothing_to_fix\"}`, never a bare acknowledgement. `files_changed` counts the linking files written (for a folder, the total over all its files). `partial` is sent only after the files left over are in `pending_fixes`; the reply is sent after the writes and the log entry and before any rescan, and the daemon's own `graph:changed` push (with the `fixes` entry) follows. The fix log decides what an event means: the same rename again, or an earlier one of a chain, is `already_applied`; a late `A to B` whose file has since moved to `C` is fixed to `C`; a rename back (`Plan` to `Training Plan` to `Plan`) is a new fix because its entry is newer; an event that disagrees with a hash-guess fix the watcher already made wins, and the links the guess wrote are re-pointed. A case-only rename (`Plan.md` to `plan.md`) is a rename on any disk: the old name counts as in use only when it is on disk spelled exactly so, which a case-insensitive disk's `stat` does not tell, and the last segment of each path keeps the case the client gave. `nothing_to_fix` is an equal pair, an old name that is a file again, a new path that is neither on disk nor in the log, a path in an ignored directory or `.tephraignore`, and a file moved outside every source (that one is also logged `uncertain`, \"vanished, moved outside sources\"). A path in no source is a `SOURCE_ERROR` (-32011) with `data.reason` `not_inside_a_source`. A missing, empty, relative or non-string path is `INVALID_PARAMS`. The watcher's own pairing of the same rename asks the same log first, so the two signals fix a rename once whichever comes first.
- `unit.list`: one folder of a source (`{source, folder?, recursive?}`), each entry `{id, name, rel_path, kind, size, mtime, title?}`, folders first then by name. Files come from the cache through a read-only connection; folders of an online source come from the disk (so empty folders show), and an offline source is listed from the cache alone with `offline: true`. `tephractl ls <source> [folder] [-r]` prints it.
- `unit.search`: a name search across every source (`{query, scope?, limit?}`; `scope` is `names` (this bullet), `headings` or `blocks` (inside one file, with `in`), or `all_blocks` (the `^^` search, below), and `limit` is 1 to 100000, default 50). Each result is `{id, source, title, kind, score, offline}`, best first. A file matches on its name, its title (front-matter title, else first heading, else the name) or its path, case-insensitively and literally (a character of the query is that character, never a wildcard): an exact name scores 1.0, then a prefix of the name, then a looser match on the name or title, then a match on the path alone. Every kind of file is searchable, including ones too large to read and those of an offline source (`offline: true`). It runs on its own read-only connection in one pass, never takes the writer gate or the shared cache lock, and never writes. It does not feed link resolution: a tie in `[[Name]]` stays an error whatever a search would rank first (a test fences the resolver against importing the search). `tephractl search <query> [--limit n]` prints one row per result; a query starting with a single `#` or `^` is refused client-side unless `--in <id>` picks the file, and one starting with `^^` is the all-blocks search (a bare or blank `^^` is refused as an empty query, with no request). It prints one row per hit as `<unit>:<line>  <kind>  <snippet>` (`<unit>  <kind>  page N|slide N #i|paragraph N  <snippet>` for a document).
- `unit.search` with `scope: "all_blocks"` (`tephractl search "^^text"`): a full-text search of every block of every source. The `block_fts` table (an FTS5 trigram index, so part of a word matches) has one row per paragraph, heading and `^id` of a note, per symbol and comment block of a code file, per blank-line-separated block of a `text-other` file and per paragraph of a document (by page, slide or paragraph, never with a block ID). A binary, a too-large file or a document with no readable text has none. The scan writes a unit's rows in the same transaction as the unit, and every delete path removes them (a unit's rows are the rowid range `unit_id << 24 ..`). A symbol's text also carries its name split into words, so `conflict` finds `ConflictReason`. The query is never FTS5 syntax: it is sent as one quoted phrase, so `NEAR`, `AND`, `"` and `*` are plain text, and one under three characters uses a literal `LIKE`. Ranked: a symbol or heading named exactly like the query first (found through `block_names`, an indexed table of those names, not by scanning matches), then bm25, then shorter path, path, source and line. The work is bounded: bm25 is computed for at most the first 10,000 rows FTS5 matches (in index order), so a query matching more than that ranks those, and a 100k-file index answers a common word in tens of milliseconds, not seconds. A row over 16K characters is not cut off: a block over that is several rows of about 2K characters, each at the line it starts on. Each result is `{unit, source, kind, line | page | slide | paragraph, index?, snippet, block_id?, offline}`. It reads one snapshot on its own read-only connection and never takes the writer gate. A cache built before this index is flagged for a rescan on start. The daemon fails to start with a clear error if SQLite has no FTS5 or trigram tokenizer.

## The fix log and pending fixes

Every automatic link fix is recorded, and work that could not be finished is kept so it survives a crash. Both live in tables of the cache that a schema-version rebuild never drops (like `sources`): `fix_log` and `pending_fixes`.

- **One rename, one log entry**, however many files it touched or how often a file was retried. The entry has an id, a time, a kind (`rename`, or `uncertain` for a file that vanished with no certain pair: "vanished, no certain pair: links broken", with no work queued), the old and new path, the result for each linking file (source, path, status) and an overall status: `applied` (every file done), `partial` (some done, some still waiting or needing a person) or `needs_manual_fix` (nothing could be written). A retry that later succeeds updates the same entry in place (`partial` to `applied`); an edit the write loop had to recover from is counted on it. The log is a record only: nothing replays or undoes it, and `tephractl fixes` never writes.
- **The work list.** Before the first file is written, the entry and one `pending_fixes` row per linking file are stored in one transaction, so there is never a row without an entry or an entry without its rows. A row is intent (file, old target, new target), not a recorded edit: each retry re-reads the file and works out the edit again. When a file is done, its row is deleted and the entry updated in one transaction.
- **Re-checks before each retry.** A row whose old name now belongs to a new file is dropped as `nothing_to_fix` (never rewritten to the wrong file). A row for a later rename of the old name to somewhere else is cancelled. A target that was renamed again (a chain A to B to C) is followed to C; one renamed or deleted with no logged rename is dropped as `nothing_to_fix`. A target in another source is left as `needs_manual_fix`.
- **Failure classes.** A permanent failure (immutable flag, ACL deny, unwritable directory, symlink, read-only mode) goes to `needs_manual_fix` at once. A transient one (the file keeps changing) is retried on a bounded backoff (`ITEM_BACKOFF_BASE`, doubling to `ITEM_BACKOFF_MAX`), at most `MAX_ITEM_ROUNDS` times, then `needs_manual_fix`. A file whose owner-write bit is off is never rewritten and its mode is never changed.
- **When rows are retried.** There is no timer. A waiting row is retried after a later watcher batch in its source once its backoff has passed, at startup (after the unfinished scans are redone) and after `source.rescan`. A `needs_manual_fix` row is retried at startup, on `source.rescan`, and when a batch changes that very file; a later edit by the user re-queues it once, from a fresh attempt count. Rows of an offline source wait and use no attempts.

## What Tephra writes

Tephra reads your files and never changes them, except through exactly three writers. Nothing else (a scan, a search, a resolve, `ls`) writes to a source. Each of the three writes a temp file beside the original, syncs it and renames it into place, and checks the file's size and mtime first: if the file changed since it was read, nothing is written.

1. **`link.apply_refactor`** rewrites the links in other files that a moved file would break. It never moves the file itself.
2. **`block.ensure_id`** adds an ID to one block: ` ^id` at the end of a note paragraph, or `// ^id`, `# ^id` or `-- ^id` at the end of a code symbol's definition line. It changes nothing else, and never creates a duplicate.
3. **The duplicate block ID rename.** When a changed file is re-parsed and an ID that the cache already held for that file once now appears more than once, the copies are renamed in one write and the original keeps its ID, so links stay on it. The original is the occurrence whose text equals the cached block's text, then the one on the cached line; if none is on that line, the nearest one below it (a copy pasted above the original pushes the original down, never up); then the first.
   - A typed ID gets a numeric suffix: `^summary` becomes `^summary-1`, then `-2`, skipping any suffix the file already uses. A Tephra-format ID (6 characters of `a-z0-9`) gets a fresh 6-character ID that is unique in the file. In a code file the ID in the copy's comment changes and nothing else on the line does.
   - The cache records the new ID straight away, and the watcher drops the file events of Tephra's own write, so a rename never starts another batch.
   - Each rename logs one line with the unit id, the old ID, the new ID and the line.
   - Only `prose` and `code` files are ever written. A `^id` inside a code fence, an inline code span, frontmatter or a string literal is not a block and is never renamed. Documents, `text-other` and binary files are never written.
   - **Not renamed:** a file that already held duplicates the first time it was scanned (including after a schema rebuild), an ID that was not in the file's cache and appears twice (a block pasted twice from elsewhere), and the same ID in two different files. Resolving such an ID gives the ambiguity error.
   - **When it runs.** A rename happens when a changed file is re-parsed, and a file is re-parsed in two ways: by a watcher batch for a source registered in the current `tephrad` run, and by a full rescan of a source whose files already have cached rows. A duplicate added while `tephrad` was stopped is therefore renamed only by the next full rescan: an interrupted scan that `tephrad` redoes when it starts, or `source.rescan`. After a clean stop and start nothing is rescanned, and `tephrad` starts no watcher for sources that are already registered, so an edit made after such a start is not renamed until the source is rescanned (or registered again).
   - If the write fails (read-only file, full disk), the file is left as it was, the reason is logged, the cache keeps the duplicate rows and the scan carries on. If another writer holds the file (`block.ensure_id`) or the file changed since it was read, nothing is written and the file is tried again, up to 8 times about 250 ms apart, reading it afresh each time; its cached rows stay as they were until then (in a rescan the file is indexed after those tries). If it is still not possible after the last try, the file is indexed as it is, with the duplicate, and `tephrad` keeps in memory the IDs the cache held for the file before that edit, so the file's next re-parse (an edit, or a full rescan) still renames the copy. That memory is dropped once the file is renamed, no longer has a duplicate or is deleted, and is lost when `tephrad` restarts: a file with a duplicate left like this then counts as one scanned with its duplicate, and is never renamed.

## Running the daemon on macOS

`tephractl daemon install` copies `tephrad` to `~/Library/Application Support/tephra/bin/`, signs the copy with a local "Tephra Local" certificate (created in your login keychain the first time) and loads it as a launchd agent (`com.danrfletcher.tephrad`), so it starts at login and is restarted if it exits with a failure. `daemon status` shows whether the agent is installed and running, and `daemon uninstall` removes the agent and the installed copy but keeps the certificate, so a later install keeps its permissions.

macOS needs a one-time Full Disk Access grant for the installed `tephrad` before it can read folders such as `~/Documents`. Until it is granted, a read the system refuses is recorded as `permission_denied` in the daemon's `access.json`, and `daemon install` and `daemon status` print the one line that fixes it: open System Settings > Privacy & Security > Full Disk Access, add `~/Library/Application Support/tephra/bin/tephrad`, then run `tephractl daemon install` again. These commands need no token and no running daemon. Off macOS, start `tephrad` by hand.
